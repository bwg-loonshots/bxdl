# BXDL UAT

현재 과업은 **실제 Ubuntu 24.04 x86_64에서 고정된 소스로 빌드하고 Linux 개발 패키지를 만드는 검증**이다. 테스터가 설치·운용 편의성 평가를 시작하기 전에 실제 Linux 산출물을 확보하는 단계다. 이번 빌드는 Java·노드·systemd를 실행하지 않는다. 설치·초기화·서비스 운용은 다음 과업으로 배정한다.

## 테스터에게 전달할 것

준비 담당자는 머지된 commit으로 키트를 다시 만들고 `deliveries/<commit 앞자리>/`에 다음 자료를 넣는다. 전달 archive와 plan의 SHA-256, source commit은 테스터에게 별도의 전달 메시지로도 알려준다. 내부 checksum 파일만으로 공급자의 신뢰를 확인한 것으로 처리하지 않는다.

| 파일 | 용도 |
| --- | --- |
| `build-kit.tar.gz` | 고정 제품 source·Linux JRE·RC.4 JAR·빌드 도구 |
| `HANDOFF.json` | 이번 전달본의 `sourceCommit`, `planSha256`, `kitArchive.sha256` 등 고정값 |
| `SHA256SUMS` | 전달 파일의 손상 여부 확인 |
| `TESTER-GUIDE.md` | 준비·실행·반환 순서 |
| `TEST-RESULTS.md` | 관측 결과·실패·도움 요청·실행 범위 기록 양식 |
| `IMPROVEMENTS.md` | 막힌 지점과 개선 의견 답변 양식 |

테스터에게는 위 파일을 담은 폴더 또는 전달용 압축 파일 하나를 보낸다. `deliveries/`에는 Git에 넣지 않는 생성물을 보관한다. 실제 전달본은 그 안의 `HANDOFF.json`이 지정한 commit을 기준으로 한다. 예전 문서에 있는 키트나 해시를 섞어 쓰지 않는다.

## 테스터에게 보낼 과업 문구

> 실제 Ubuntu 24.04 x86_64 장비에서 첨부한 `TESTER-GUIDE.md`의 빌드를 실행해 주세요. SSH 계정·비밀번호·개인키를 공유할 필요는 없습니다. 먼저 환경과 전달 파일을 확인하고, 빌드 성공 시 만들어진 두 패키지와 빌드 기록을 반환해 주세요. 실패해도 원인을 임의로 우회하지 말고 중단 지점·오류 코드·소요 시간·도움이 필요했던 내용을 적어 주세요. `TEST-RESULTS.md`와 `IMPROVEMENTS.md`도 작성해 주세요. 이번에는 노드 설치·초기화·서비스 시작을 하지 않습니다.

처음에는 환경 확인과 빌드를 위한 시간을 별도로 잡는다. 도구 설치나 네트워크 문제로 시간이 더 필요하면 그 자체를 기록한다. 성공 여부와 사용 편의성 평가는 별도 항목으로 받으며, 도움을 받아 성공해도 도움의 종류와 횟수를 남긴다.

## 결과를 받는 담당자

1. 반환 압축 파일의 SHA-256과 별도로 받은 receipt SHA-256을 대조한다.
2. 반환 원본을 보존하고 정제된 기록과 실제 산출물을 구분한다. 개인 장비 경로·자격증명·미정제 로그를 Git에 올리지 않는다.
3. [Linux 수신 검증 절차](../docs/linux-native-build.md)의 도구를 신뢰하는 로컬 CLI와 함께 사용한다. 받은 Linux 실행 파일을 Mac에서 실행하지 않는다.
4. archive·manifest·A/C·Java·JAR 해시를 고정하고, 빌드 성공과 엔진/native·systemd 인수 상태를 별도로 기록한다.
5. 관측된 막힘과 개선 제안을 원인·재현 조건·영향도·우선순위로 분류한다. 실제 설치·운용 UX 과업은 기술 인수 범위를 정한 후 추가한다.

## 폴더 운영

- 이 폴더의 안내서와 빈 양식은 버전 관리한다.
- `deliveries/`는 생성된 키트·전달 사본을 보관하며 Git에서 제외한다.
- `runs/`는 수신한 개별 기록의 로컬 보관 장소로 사용할 수 있으며 Git에서 제외한다. 반환자의 동의와 검토를 거친 정제 결과만 별도 `results/` 문서로 작성한다.
- 채워진 기록의 `NOT_RUN`, `BLOCKED`, `FAIL`을 임의로 PASS로 바꾸지 않는다. 어떤 commit·키트·장비·실행에서 나온 결과인지 함께 보존한다.
